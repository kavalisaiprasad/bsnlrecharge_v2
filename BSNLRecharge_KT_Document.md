# BSNL Recharge Application - Knowledge Transfer Document

**Document date:** 18 November 2026  
**Repository:** `bsnlrecharge_v2`  
**Application type:** React single-page application (SPA)  
**Primary purpose:** Validate a BSNL prepaid mobile number, show recharge plans and active-plan details, validate a recharge request, and open the payment gateway.

---

## 1. Executive Summary

This repository contains a React 18 frontend for a BSNL prepaid mobile recharge flow. It does not contain a backend or database implementation. Recharge and plan data are obtained from an external API at `https://bsnlrechargeapi.pyrogroup.com`.

The normal user flow is:

1. Enter a 10-digit mobile number.
2. The frontend fetches the operator, circle, active plan, expiry date, and recommended plans.
3. Complete the CAPTCHA.
4. Enter an amount or select a plan.
5. Submit the recharge request to the backend validation API.
6. The backend returns a payment gateway URL.
7. Open the payment gateway in a new tab after confirmation.

The active recharge implementation is [src/components/Recharge/Recharge.js](/home/sathish/bsnlrecharge_v2/src/components/Recharge/Recharge.js). Two additional recharge variants exist in the repository but are not registered in [src/App.js](/home/sathish/bsnlrecharge_v2/src/App.js).

## 5. Active Recharge Flow

The active component is [src/components/Recharge/Recharge.js](/home/sathish/bsnlrecharge_v2/src/components/Recharge/Recharge.js).

### 5.1 State

Important state includes:

- `mobile`: entered 10-digit number
- `operatorCode` and `circleCode`: operator/circle details
- `circle_code`, `zoneCode`, `validation_api_url`: recharge validation parameters
- `activePlan`, `Expiry_date`: current BSNL plan details
- `topPlans`, `recommendedPlans`: recommended-plan data
- `plans`: categorized plan list
- `price`, `plan`, `des`: selected amount, product code, and description
- `captcha`, `userInput`, `isCaptchaValid`: CAPTCHA state
- `pgUrl`: payment gateway URL returned by validation
- `showConfirmModal`, `showResultModal`: result/confirmation dialogs
- `errorMessage`, `resultMessage`, `resultType`: validation and API feedback

State is local React state; no Redux or persistent browser storage is used.

### 5.2 Mobile Number Operator Lookup

After every mobile input change, the component requires exactly 10 digits. A valid 10-digit value triggers:

```text
GET https://bsnlrechargeapi.pyrogroup.com/bsnl-api/fetch-operator?mobile=<10-digit-mobile>
```

Expected successful response fields include:

- `status`: `SUCCESS`
- `operatorCode`: for example `BSNL`
- `circleCode`
- `circle_code`
- `zone_code`
- `validation_api_url`
- `active_plan`
- `Expiry_date`
- `topplans`
- `recommended plans`

If the operator is not BSNL, the component shows an invalid-mobile message. Failed responses and network exceptions also reset operator and plan state.

### 5.3 CAPTCHA

The CAPTCHA is generated in the browser using a six-character alphanumeric string. The user input is checked only in client-side React state.

Important limitation: this CAPTCHA is not a server-side anti-bot control. It prevents casual form entry only and should not be considered an authentication or security boundary.

### 5.4 Plan Retrieval

When the user chooses **Browse Plans** or opens the plan modal, the component requests:

```text
GET https://bsnlrechargeapi.pyrogroup.com/api/recharge-plansnew?operatorCode=<operator>&circleCode=<circle>
```

The response is expected to contain `mobilePlans`, an object grouped by service category.

Categories are normalized and ordered as:

1. Voice
2. Data
3. Voice & Data
4. Topup
5. VAS pack
6. International Roaming

The plan modal displays tabs for each category. Plans are sorted by descending price.

### 5.5 Delhi/Mumbai Special Plans

For normalized Maharashtra or Haryana circles, the component adds a synthetic special tab:

- Maharashtra -> Mumbai Exclusive
- Haryana -> Delhi Exclusive

These plans are hard-coded in `Recharge.js`, rather than being returned by the external plan API.

Maintainers must verify these hard-coded amounts, validity periods, and descriptions when tariffs change.

### 5.6 Amount Entry

The amount field is free text and may be entered directly. After an amount is entered, the component calls the plan API again and attempts to match the amount to a plan description.

Plan selection sets:

- amount/price
- product code/plan
- plan description
- selected-plan state
- visible plan announcement for assistive technology

### 5.7 Recharge Validation

The submit/recharge action sends:

```text
POST https://bsnlrechargeapi.pyrogroup.com/bsnl-api/validate
Content-Type: application/json
```

Request body:

```json
{
  "destMsisdn": "<mobile>",
  "denomination": "<selected amount>",
  "zone_code": "<zone>",
  "circle_code": "<circle>",
  "url": "<validation_api_url>"
}
```

Success condition:

- HTTP success
- `result.message === "DIAMETER_SUCCESS"`
- `result.data.pgurl` contains the payment gateway URL

The UI then opens a confirmation modal. Confirmation opens `pgurl` in a new browser tab using `target="_blank"`.

Failure conditions display `status_desc`, `error`, `message`, or a generic recharge request failure message.

## 7. API Contract Summary

| Operation | Method | Endpoint | Key inputs | Key outputs |
|---|---|---|---|---|
| Fetch number/operator details | GET | `/bsnl-api/fetch-operator` | `mobile` | operator, circle, active plan, expiry, top plans |
| Fetch recharge plans | GET | `/api/recharge-plansnew` | `operatorCode`, `circleCode` | categorized plans |
| Validate recharge | POST | `/bsnl-api/validate` | MSISDN, denomination, zone, circle, validation URL | payment gateway URL or error |

The API host and endpoints are hard-coded. There is no environment-based configuration, for example through `REACT_APP_*` variables.

Any API changes require source updates and a new production build.

## 9. Deployment

The application can be deployed as static files using the contents of `build/`:

```bash
npm run build
```

Serve `build/` through an HTTP/static server configured for SPA routing.

Example with a static server:

```bash
npx serve -s build
```

Deployment requirements:

- The server must route unknown paths to `build/index.html`.
- External API calls must be allowed by the browser.
- HTTPS is recommended for the frontend and payment gateway.
- Confirm CORS support on `bsnlrechargeapi.pyrogroup.com`.
- Confirm whether third-party cookies or popup blockers affect the payment gateway.

The deploy server should not expose source maps because `GENERATE_SOURCEMAP=false` is used.

## 12. Known Risks and Improvement Areas

### Functional

- Payment success is static and does not verify backend payment status.
- There is no transaction receipt or payment callback handling in the frontend.
- Plan descriptions and hard-coded circle plans can become stale.
- Amount entry is not strongly validated as numeric or within a tariff range.
- Mobile numbers are checked only for length and digits.
- API response field names are not validated with explicit schemas.
- A failed plan fetch silently produces an empty plan list.

### Security

- CAPTCHA runs only in the browser and can be bypassed.
- No authentication/authorization layer exists in this repository.
- Frontend validation must be repeated by the backend.
- The external validation API and returned payment URL must be trusted.
- Popup handling with `target="_blank"` should include `noopener`; `rel="noopener noreferrer"` is already present on the confirmation link.

### Reliability

- API hosts and endpoints are hard-coded.
- No retry, cancellation, or timeout policy is implemented for fetch calls.
- The component can issue the plans API repeatedly.
- Fast mobile-number edits can overlap network requests, and stale results are not explicitly canceled.
- No loading or skeleton state is implemented for the operator lookup.

### Testing

- The existing test suite is a default CRA placeholder and does not test functionality.
- No focused tests cover operator lookup, CAPTCHA, plan selection, validation, or routing.
- No environment or API mocking is configured.

### Maintainability

- `Recharge.js` is long and combines form, API, state, plan, modal, and presentation logic.
- Commented-out code and `Recharge_discount.js` variants can confuse maintainers.
- Build warnings report unused variables and one redundant nested block.
- The README is generic and does not describe this application.

## 13. Suggested Handover Sequence

For a new developer:

1. Read `src/index.js` and `src/App.js`.
2. Open `src/components/Recharge/Recharge.js`.
3. Run `npm start` and test the flow with a valid BSNL test number.
4. Record the real API response shape from:
   - `fetch-operator`
   - `recharge-plansnew`
   - `validate`
5. Confirm payment callback behavior with the backend/payment gateway team.
6. Replace hard-coded API host configuration with environment variables.
7. Replace the static success page with real callback/status handling.
8. Add focused React tests and API mocks.
9. Remove or clearly archive alternate recharge implementations.
10. Rebuild and deploy the `build/` output through an SPA-capable server.
